# FoodFlow frontend audit

> เอกสารนี้เป็น snapshot ก่อนแก้ ใช้เก็บหลักฐานเดิม สถานะ implementation ล่าสุดดู [คู่มือฟีเจอร์](../features.md) และ remediation results; ตัวเลข/ข้อค้นพบด้านล่างไม่ใช่ผลหลังแก้


Repository `D:/foodflow/app`, revision `2dc0dcc`. Reviewed the POS, kitchen, serve, Counter, menu/media, customer Display, promotions, members, report, and import flows and the shared React cache, API, and session code. Paths below are relative to the repository. Priority reflects the operational consequence.

## Verification

- `rtk npm --prefix app/frontend test` exited 0 across 8 pure-function test files. `rtk npm --prefix app/frontend run build` exited 0. Those suites do not mount the affected UI.
- `rtk node audit-evidence/frontend-repro.cjs` exited 0 across eight browser scenarios through local Vite at port 5173 and Edge. It aborts WebSockets, intercepts API/PostgREST traffic, uses synthetic records, and allows only local asset GET requests to pass through. The script asserts the current defects so it should fail on those cases once fixed.
- `rtk node audit-evidence/frontend-logic-repro.mjs` exited 0 and confirmed cache ordering/invalidation and a promotion selection counterexample.
- Findings marked **Browser** or **Node** have executable local reproduction. Other findings are source review. Real payments, printer output, live Realtime timing, a full screen reader sweep, and full production operation were outside the verified scope. The existing real-environment roles suite is documented as 10/10 in `docs/project-readiness.md:40–44`. The order-flow suite writes to its configured database and was excluded from this audit.

## New findings

| ID and priority | Evidence and impact | Remedy and acceptance |
| --- | --- | --- |
| FE-01 P1 · The live bill changes after the PromptPay QR is shown · **Browser** | `frontend/src/pages/Counter.tsx:74–85,188–224,331–348` groups by table, derives live totals, and confirms the latest list. The open QR changes from ฿100 to ฿200 after another order appears, and confirmation includes both orders. A guest can scan ฿100 and the cashier can then successfully mark a ฿200 bill as paid. `database/migrations/0002_display_payment_reports.sql:517–523,553–563,579–590` validates statuses and calculates the current amount, with no confirmed total or quote identity. | Bind the amount, order IDs, payment method, promotion and points to a payment quote. If terms change, require a new explicit confirmation or reconcile a transfer against the original quote. Verify adding a served order, a promo expiry, and a double-counter race while a QR is open. |
| FE-02 P1 · An ABB can print another order’s items as an artificial discount · **Browser** | Counter permits partial issuance using `Promise.allSettled` (`frontend/src/pages/Counter.tsx:63–72`). `frontend/src/components/Receipt.tsx:71–83` uses the combined receipt when exactly one ABB exists. `Receipt.tsx:257–275,350–359` calculates a discount from aggregate line gross and that ABB’s single-order amount. With two ฿100 orders and only the first ABB present, the ABB showed both sets of lines and a fabricated ฿100 discount. | Tie every ABB to `doc.order_id`. Indicate which paid orders still lack a document and provide the appropriate receipt/retry path. Test zero, one partial, and all ABBs for a two-order table and verify each printed amount and line scope. |
| FE-03 P1 · Failed settings read silently forces default cash and suppresses all receipt/ABB handling · **Browser** | `frontend/src/lib/shop.ts:21–35` converts every settings error to `null`. `frontend/src/pages/Counter.tsx:199–223,307–331` then shows a cash-style payment button, omits payment fields, and passes no IDs to receipt/ABB processing. A successful mocked payment after a settings HTTP 500 produced no receipt request. SQL default is cash at `0002_display_payment_reports.sql:517–523`. A cashier who already took card or transfer could create a cash sale, skewing reconciliation. | Distinguish pending, absent row, and connection failure. Keep valid cached settings identifiable as stale, block confirmation when method is unresolved, send the explicit method, and retrieve receipts independently of optional settings. Verify pending reads, no settings row, 500, then recovery. |
| FE-04 P1 · An old CSV preview unlocks import of newly selected data · **Browser** | `frontend/src/pages/Import.tsx:41–74,92,112–125,142–145`. Start dry run on A, choose B while it is pending, then wait for A. The preview displays B’s name and enables submission of B’s CSV without a dry run on B. The same race applies to `skip_unknown`. Server validation can still reject malformed input, but a valid unreviewed dataset can be committed. This extends P2-B6, which tracks stale file reads and invalid selection. | Key the preview by exact file content/version and options. Abort or discard stale reads and previews and verify the preview still matches at commit time. Exercise A→B, switch skip during pending preview, file-read rejection, and a stale response after an invalid selection. |
| FE-05 P1 · Promotion read errors look like an empty selection at checkout · source | `frontend/src/components/PromoPicker.tsx:11–35,38–40` treats a failed promotions read as an empty array and failed link reads as all-bill scope. `frontend/src/pages/Counter.tsx:188–215` always sends a selection, including an empty list if the promotions read fails. `0002_display_payment_reports.sql:561–563` invokes `apply_promotions` for that array and `0001_core.sql:1746–1756,1839–1855` removes and recalculates existing discounts. A read failure can remove a discount already applied to the order. Missing link data can also produce a different preview from the SQL result. | Expose promotion readiness and retain the last consistent snapshot. Prevent checkout when the amount depends on incomplete rules, or offer a server quote that preserves the recorded prices and promotions. Verify failures of promotions, availability, and link reads individually with an existing discount and a scoped discount. |
| FE-06 P2 · Account/request lifetimes diverge · **Browser** for stale 401, source for UI state | `frontend/src/lib/api.ts:22–40,45–55` clears whichever session is active when an authenticated 401 comes back, even after the user switched accounts. The synthetic late 401 signed out the replacement account. `frontend/src/lib/auth.ts:46–74,80–105` keeps role state independently of the current user, persists prior staff lookups inside the loader, and never refreshes a mounted view until the user ID changes. `frontend/src/components/RequireRole.tsx:48–66,184–189` can briefly render the previous role/restaurant state on a storage-driven identity switch. `frontend/src/lib/session.ts:22–35,69–77` checks expiration during access and receives tab updates, with no timer/event for an idle protected view. Server RLS/API role enforcement remains the authorization boundary. | Tie requests, staff state, saved role hints and mounted protected screens to session generation plus user/restaurant. Ignore superseded 401s and storage writes, and handle expiry/revocation explicitly. Verify account A’s late request leaves B signed in, no prior view renders on a direct cross-tab switch, and an expired idle screen transitions to sign-in. |
| FE-07 P2 · Payment and member controls have keyboard and viewport gaps · **Browser** for QR | `frontend/src/pages/Counter.tsx:307–348` sets `aria-modal` but leaves focus on the underlying trigger and does not close on Escape. The confirmation button also overflows a 640×320 viewport under a fixed overlay with visible overflow. `frontend/src/pages/Members.tsx:91–101` uses pointer-only row selection. `frontend/src/pages/Promotions.tsx:225–236` hides native day checkboxes with `display:none`. Import file picker at `Import.tsx:112–125` has no associated label. Status results such as POS submit at `Pos.tsx:359–360` have no status/alert semantics. | Use a shared modal with initial/contained/restored focus, Escape behavior, and a scrollable viewport. Add native member selectors, visually hidden focusable day checkboxes with focus styles, explicit field labels, and status/error announcements. Verify keyboard-only workflows, short landscape and 320px portrait, screen reader announcements, and absence of activation behind the dialog. [W3C modal dialog pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/) · [WCAG 2.2 keyboard](https://www.w3.org/WAI/WCAG22/Understanding/keyboard.html) · [Labels or instructions](https://www.w3.org/WAI/WCAG22/Understanding/labels-or-instructions.html) · [Status messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html). |
| FE-08 P2 · “Best” automatic promotion selection misses a larger valid discount · **Node** | `frontend/src/lib/discount.ts:74–92` greedily takes the largest scoped offer, blocking compatible smaller offers. On a bill with A and B at ฿100 each, a single ฿60 offer for A/B excludes two independent ฿40 offers. The app auto-selects ฿60 rather than the available ฿80. `frontend/src/components/PromoPicker.tsx:42–63` also retains manually selected rules across line changes, so selections that originally did not overlap can later overlap and fail SQL validation. Related to P2-F1’s stacking work. | Define the required optimality and ties within the SQL promotion cap. Compute and validate a consistent selection, including the manual selection on line changes. Verify the ฿60/฿80 fixture and shared item added to a previously non-conflicting manual pair. |
| FE-09 P2 · Pending member lookup can link a different phone than staff last typed · source | `frontend/src/components/MemberBox.tsx:32–42,45–57,113–132` captures a phone when requesting and leaves the input editable. Type phone B while A is pending; A can become the selected member after B is visible, or A’s not-found result can offer registration for B. A payment can attach points/discounts to the unintended account. This extends P2-B3’s Members search/ledger fixes. | Bind lookup/registration and displayed state to the submitted phone and bill identity. Invalidate the result when input changes and visibly reset linked points. Verify delayed lookup success/not-found, editing while pending, and opening the next bill. |
| FE-10 P2 · Inventory filter screens can keep earlier results and mutation actions · source | `frontend/src/lib/stockApi.ts:251–282` gates only by key equality. A forced reload of the same key can be overwritten or have its loading cleared by an older response. A new uncached key retains prior data until it resolves, including on failure. Stock history at `frontend/src/pages/StockHistory.tsx:20–43,62–63,91–145` retains rows/results and the reversal path while filters change. This extends P1-B5 to the shared stock loader. | Store results with an identity, blank or label the previous snapshot and disable its mutations on new filters, and check sequence/key/session on all paths. Verify a slow old reload and a failed uncached filter while old reversible rows exist. |
| FE-11 P2 · Losing a route bundle can leave a blank app · source | `frontend/src/App.tsx:7–30,40–80` uses lazy modules with a Suspense loading fallback. `frontend/src/main.tsx:7–13` has no error boundary. A rejected chunk on poor connectivity or a deployment with a retired asset can unmount the root. Preloading catches its own failure only (`frontend/src/pages/loaders.ts:34–57`). | Add route-level recovery and offer retry/reload without resetting unrelated state. Simulate a rejected dynamic import on navigation and verify an accessible error, safe retry, and access back to a working page. |
| FE-12 P2 · Order entry allows drafts that exceed RPC limits, and a table bill can exceed its payment cap · source | `frontend/src/pages/Pos.tsx:101–118,134–150` caps quantity per line but has no 50-line guard. `0003_users_inventory.sql:880–893` rejects more than 50 lines. Counter groups all open table orders (`Counter.tsx:74–85,208–215`) and `0002_display_payment_reports.sql:543–545` rejects more than 50 IDs. A single large order can never submit as drafted, and a dinner accumulating 51 tickets cannot be paid from Counter. | Enforce or deliberately revise both limits. Offer an actionable early split or throughput-safe payment grouping. Verify 50/51 lines and 50/51 orders on one table. Related to split bills in P1-F3. |
| FE-13 P2 · Customer Display may keep a revoked menu visible until polling · source | `frontend/src/pages/MenuAdmin.tsx:146–149` says displays stop immediately. `frontend/src/pages/Display.tsx:29,393–408` polls every 60 seconds and keeps the last content indefinitely on request error. Overlapping requests and token changes also lack a generation check. A slower valid response can replace newer invalid state. | Agree on revocation latency, discard outdated/token-mismatched responses, and cap the age of content shown while disconnected. Verify 200→revoked with a pending older 200, token A→B, and offline recovery. Related to P1-B6’s pointer timer cleanup. |

Additional UX evidence: the Report UI uses device-local date as the default (`Report.tsx:13–17`), while daily reporting uses the shop timezone. Make the shop date or its timezone visible and use the same day definition as the report RPC, including for foreign-timezone terminals. Report, Members, Promotions and Receipt still direct users to archived migration numbers on broad load failures (`Report.tsx:23`, `Members.tsx:36`, `Promotions.tsx:50–52`, `Receipt.tsx:76–79`). Use recovery specific to network failure, authorization, or an actual schema mismatch.
