> เอกสารนี้เป็น snapshot ก่อนแก้ ใช้เก็บหลักฐานเดิม สถานะ implementation ล่าสุดดู [คู่มือฟีเจอร์](../features.md) และ remediation results; ตัวเลข/ข้อค้นพบด้านล่างไม่ใช่ผลหลังแก้


Reviewed the current `app` source and the effective numbered migrations through `0008`. The route checks use Hono with a mocked Supabase/LINE transport and test-only signing material. They exercise the current implementation without contacting a project database or changing production code. An assertion passing means it reproduced the described behavior. The SQL findings below follow from the effective migration definitions.

## P0 - A restaurant administrator can reset an identity shared by other restaurants

`POST /staff/:userId/reset-password` checks the caller and target roles for the requested restaurant, then calls the service-role password setter and returns the temporary credential. `staff_list` filters by one restaurant before aggregating roles. The password setter updates by global user ID. The membership key includes restaurant ID, and the staff creation flow deliberately reuses a global user ID found through email. A manager of shop A can therefore reset an employee who is staff in A and owner in B. The change also denies the employee use of their existing password across shops. This exists even when each RLS check grants the correct local role. [Reset route](../../backend/src/app.ts#L408) / [Account reuse](../../backend/src/app.ts#L361) / [Membership key](../../database/migrations/0003_users_inventory.sql#L92) / [Staff lookup](../../database/migrations/0003_users_inventory.sql#L357) / [Global password setter](../../database/migrations/0003_users_inventory.sql#L288)

The offline route probe modeled both memberships and observed HTTP 200 plus a global setter call. Move shared-account recovery to an identity-level verified flow. If local administrators retain single-restaurant reset rights, enforce eligibility inside the same database transaction as the password change, including concurrent membership changes. Regression should reject the cross-shop case, preserve allowed recovery, and avoid exposing other memberships or returning the global credential to a shop administrator. [Offline evidence](D:/foodflow/audit-evidence/backend-audit.test.mjs#L44)

## P1 - Password reset, deactivation and first-login state are unenforced in issued sessions

The Worker issues the same authenticated bearer whether `must_change_password` is true or false. The protected middleware checks `is_active` only. The flag currently drives a frontend redirect. The direct browser Supabase/Realtime client uses the same bearer, and the core RLS helpers compare the `sub` with memberships without checking account state. The Worker declines a disabled account while direct policy paths that depend on those helpers can still grant the old token's membership rights. Password change/reset updates only the hash and flag, leaving earlier signed tokens usable until expiry while the account remains active. Default expiry is 12 hours and configuration allows up to 30 days. Browser logout only clears local state. [JWT issue and guard](../../backend/src/app.ts#L135) / [Password change](../../backend/src/app.ts#L197) / [Database account state](../../database/migrations/0003_users_inventory.sql#L281) / [Direct browser client](../../frontend/src/lib/supabase.ts#L10) / [RLS helpers](../../database/migrations/0001_core.sql#L129) / [Role helper](../../database/migrations/0001_core.sql#L323) / [Frontend gate](../../frontend/src/components/RequireRole.tsx#L61)

The mock test signed in with a first-login flag and immediately received 200 from a role-protected staff read. Issue a narrowly scoped first-login credential and issue the full session after a successful change. Revoke earlier sessions on reset, disable and server-side logout using a session identifier or credential epoch enforced on the Worker and direct database paths. Test existing Realtime subscriptions separately, given that the local audit did not exercise the provider. Check direct table reads, sensitive RPCs and `/api/*` with old, first-login and replacement tokens. [Offline evidence](D:/foodflow/audit-evidence/backend-audit.test.mjs#L71)

Login and self-service password change always use per-isolate memory; they pass `undefined` to the limiter even though the Worker has an AI-only binding. Clearing the entire map above 10,000 keys drops active counters, confirming documented P2-B1. Unknown-email attempts also create counters and both keys are charged before either result is enforced, so blocked IP traffic can consume account buckets. `CF-Connecting-IP` relies on verified Cloudflare ingress; absence falls back to a shared `local` bucket. No production header-spoofing claim was verified. Use a shared bounded store for auth, handle capacity without clearing active windows, and exercise two isolates and a full window without leaking account existence. [Login limiter](../../backend/src/app.ts#L151) / [Password limiter](../../backend/src/app.ts#L205) / [Memory limiter](../../backend/src/guards.ts#L9) / [Binding](../../backend/wrangler.toml#L21) / [Existing task](../../docs/tasks/2-people/person-2-crm-ops.md#L9)

## P1 - Accounting exports and document lists silently omit rows

The journal export calls a row-returning RPC once. Its SQL caps at 50,000 journal lines, independently of the PostgREST response cap. Its last line can split a multi-line entry, leaving a generated journal unbalanced. Manual-expense export selects one unpaginated result. Journal, expense and tax-document lists similarly return capped arrays with no `has_more`/cursor; 1,000 tax documents over the selected dates can also make the UI totals incomplete. Monthly tax exports use `selectAll`, but it assumes a 1,000-row page and silently stops at 200,000. A platform row limit lower than the assumed page terminates iteration early. [Journal export](../../backend/src/accounting.ts#L119) / [Manual-expense export](../../backend/src/accounting.ts#L174) / [Report pagination](../../backend/src/accounting.ts#L193) / [Journal cap](../../database/migrations/0004_accounting.sql#L1215) / [Expense list](../../backend/src/accounting.ts#L431) / [Tax document cap](../../backend/src/tax.ts#L186) / [UI totals](../../frontend/src/components/accounting/AcctTax.tsx#L52)

Export against a consistent, deterministically ordered dataset and include all complete entries. Page interactive lists with an explicit cursor. Either complete a capped export via a job or return an explicit bounded result. Regression should export above the PostgREST cap and across a page boundary within a journal entry, then reconcile line IDs and debits/credits. The configured production row cap was outside audit scope.

## P1 - Post-commit failures are returned as failed accounting/tax operations

Day close commits in `acct_close_day` and then looks up LINE settings and sends a push. Settings-read failure escapes, and a network failure thrown by `fetch` does not become `LineError`. The client receives 500 even though the date is closed, and a retry receives `already_closed`. Shift close similarly commits before report and tax-document reads, and retrying receives `shift_closed`. Tax `confirm:true` creates a draft before confirmation in another RPC. Recognized domain errors return `document_id`, while transport and unexpected errors can leave a draft without returning its ID. Confirmation itself has a locked single-numbering transaction and can report `not_draft` after a successful response was lost. [Day-close route](../../backend/src/accounting.ts#L576) / [Day-close transaction](../../database/migrations/0004_accounting.sql#L1288) / [LINE transport](../../backend/src/reports.ts#L10) / [Shift close route](../../backend/src/accounting.ts#L782) / [Shift transaction](../../database/migrations/0006_tax_shifts.sql#L1087) / [Tax create/confirm route](../../backend/src/tax.ts#L124) / [Tax confirm transaction](../../database/migrations/0006_tax_shifts.sql#L758)

The offline probe supplied a successful close RPC and a failed settings query and observed 500. Return committed state on a failed notification, record delivery separately, and make close reports retrievable by ID. Give draft creation and confirmation explicit recoverable outcomes and an idempotency mechanism. Regression should simulate failure before commit, after commit and after commit with a lost response. A retry should recover the original outcome without re-closing the day/shift or issuing another tax number. [Offline evidence](D:/foodflow/audit-evidence/backend-audit.test.mjs#L122)

## P1 - Import does not identify duplicates and can silently rewrite source data

Each committed `import_sales_history` call generates a new batch and new order IDs. Import is atomic within one RPC, and a blocked preview does not write records. Resubmitting identical sales after a lost response or accidentally importing the same period twice creates another paid history batch. A valid price omitted in the CSV resolves from the current menu again at commit, so a menu price change after preview changes the eventual imported value. The parser strips every comma before testing price syntax, silently changing a malformed quoted `1,2` to `12`, and truncates references before grouping, potentially combining distinct bills. Embedded/unmatched `"` is accepted by the tokenizer, confirming the parser part of documented P2-B6. [Import route](../../backend/src/app.ts#L225) / [Import transaction](../../database/migrations/0001_core.sql#L1146) / [Parser state](../../backend/src/csv.ts#L22) / [Price and reference parsing](../../backend/src/csv.ts#L131) / [Existing task](../../docs/tasks/2-people/person-2-crm-ops.md#L41)

Validate quoting and numeric grouping before normalization. Preserve source reference identity and define a batch idempotency key plus duplicate-preview behavior. Bind commit to reviewed normalized rows or warn and require a fresh preview when price/mapping changes. Regression should run one identical batch twice, price-change between preview and commit, include distinct long references, and reject any malformed row without inserting orders. For history records, the existing accounting trigger deliberately skips imported orders. [Offline parser evidence](D:/foodflow/audit-evidence/backend-audit.test.mjs#L89) / [Accounting exclusion](../../database/migrations/0008_fix_accounting_stock.sql#L137)

## P2 - Scheduled LINE reports use wall-clock date and have no durable delivery identity

`REPORT_HOUR=''` becomes 0, while midnight selects the opening day instead of the just-completed local day. Cron ignores `ScheduledController.scheduledTime`, and `daily_report_targets` uses database `now()` to choose the hour and date. A delayed execution can miss the window. Every invocation for the same restaurant/hour can send again. A failure is logged and the hour moves on without a durable delivery attempt. The production ability to run this at all depends on the Worker deployment; the Pages entry point only handles HTTP, as documented. [Report scheduler](../../backend/src/reports.ts#L19) / [Scheduled event](../../backend/src/index.ts#L9) / [Local target selection](../../database/migrations/0002_display_payment_reports.sql#L829) / [Cron configuration](../../backend/wrangler.toml#L29) / [Existing task](../../docs/tasks/2-people/person-2-crm-ops.md#L36)

The effective daily-report SQL also selects paid revenue and payment totals by `created_at`, while accounting uses `paid_at`. An order opened before midnight and paid after midnight moves between daily dashboards. Define whether each metric measures order creation or payment, apply that rule consistently, and validate Bangkok midnight, a non-hour timezone, delayed cron, repeated cron, failures and replay. Store one dispatch per restaurant/report date and use provider idempotency for ambiguous transport outcomes. [Effective daily report](../../database/migrations/0008_fix_accounting_stock.sql#L60) / [Accounting date](../../database/migrations/0008_fix_accounting_stock.sql#L27) / [Offline dispatch evidence](D:/foodflow/audit-evidence/backend-audit.test.mjs#L99)

## P2 - HTTP validation can silently persist the wrong fields or amounts

Shared `body()` turns invalid JSON, arrays and null into `{}`. `PATCH /auth/me` sends both fields unconditionally, and the database converts omitted fields to null. An invalid body can clear both fields while returning 200, and a display-name-only update clears a saved phone. Accounting uses `Number(...)` on raw inputs; the offline day-close check observed `true` becoming ฿1 at the RPC. Equivalent coercions affect expense, supplier payment, opening balance and cashier-shift money. `Date.parse` can normalize an impossible date such as `2026-02-30`, leaving PostgreSQL to reject it as a generic input error. Buyer/supplier tax IDs and branch codes are trimmed and sliced before validation, allowing extra suffix text to be discarded. [Body and profile](../../backend/src/app.ts#L35) / [Profile write](../../backend/src/app.ts#L185) / [Database profile update](../../database/migrations/0003_users_inventory.sql#L327) / [Accounting validators](../../backend/src/accounting.ts#L65) / [Expense fields](../../backend/src/accounting.ts#L444) / [Cash close](../../backend/src/accounting.ts#L576) / [Tax input](../../backend/src/tax.ts#L88)

Treat malformed JSON separately from a well-formed object, distinguish omission from explicit clearing on PATCH, and validate finite exact money and real calendar dates before writes. Validate business identifiers before transformation. Import sets a JS string-length cap only after full request decode; enforce a byte limit for requests as well as row/field limits. Regression should verify 4xx without storage writes for bad JSON/booleans, impossible dates, out-of-range money, and overlong identifiers, plus preservation of omitted fields. [Offline validation checks](D:/foodflow/audit-evidence/backend-audit.test.mjs#L122) / [Import cap](../../backend/src/app.ts#L225)

## P2 - Public API contract and operational errors drift from execution

OpenAPI's operation/method parity test passes, but checks no request or response schema against runtime. The profile schema describes optional string fields, while malformed or omitted values take the destructive path above. Money has JSON numeric schemas, but accepts booleans and arrays through JS coercion. The general error handler returns selected PostgreSQL error messages verbatim, some of which can contain a relation or constraint name and submitted values. The Supabase client JSON-decodes response text before checking status; an upstream HTML outage falls through to an unclassified 500. All Supabase/LINE fetches here lack a per-request timeout. Known dependency failures should have predictable 502/503/504 responses while unexpected failures are logged with a request ID and sanitized details. Apply actual schema validation and verify documented status and error mappings with malformed input and dependency failures. [OpenAPI profile](../../backend/src/openapi.ts#L359) / [OpenAPI account money](../../backend/src/openapi-accounting.ts#L288) / [Parity tests](../../backend/test/openapi.test.ts#L11) / [Worker error mapping](../../backend/src/app.ts#L94) / [Supabase transport](../../backend/src/supabase.ts#L24)

Tax and accounting object writes should consistently bind the restaurant supplied in the API request to the object being updated. For example, tax creation checks `restaurant_id` in the Worker but passes only order/ref IDs to SQL, where role is checked in the object's restaurant. Expense void and journal reversal take the same pattern. SQL prevents a caller lacking authorization on the actual object from writing it. A caller with roles in both shops can still commit a write into the wrong one with a mismatched client context. Regression should reject mismatches even when the caller has valid permissions in both. [Tax route](../../backend/src/tax.ts#L104) / [SQL object resolution](../../database/migrations/0006_tax_shifts.sql#L535) / [Expense void route](../../backend/src/accounting.ts#L505) / [Reversal route](../../backend/src/accounting.ts#L545)

## Export safety and capability observations

Shared CSV generation prefixes leading formula markers (`=`, `+`, `-`, `@`, tab and CR), escapes delimiters, and keeps numeric negatives numeric. XML workbook cells are typed explicitly. Leading LF/whitespace and importer-specific formula recognition need app-level Excel/LibreOffice verification before claiming complete coverage. CSV also does not preserve all identifier display semantics during spreadsheet auto-import, including leading-zero tax IDs. [CSV and workbook writers](../../frontend/src/lib/accounting.ts#L364) / [Export tests](../../frontend/tests/accounting.test.ts#L217)

HTTP exposes shift open, cash movement and close, while the UI uses a direct RPC for X/Z reports and shift history/retrieval is absent from the HTTP interface. Tax draft editing and voiding are present through direct RPC in selected UI paths, with no equivalent HTTP operations. OpenAPI correctly mirrors the existing HTTP route set. Closing those gaps would let external consumers retrieve outputs and recover draft workflows without Supabase-specific endpoints. XML generation and download are implemented, while XSD conformance, signing and filing are separate from the delivered feature. The audit makes no tax-compliance or provider-delivery claim. [Shift routes](../../backend/src/accounting.ts#L744) / [Direct shift report](../../frontend/src/lib/tax.ts#L339) / [Direct draft void](../../frontend/src/components/TaxDocModal.tsx#L350) / [XML readiness](../../frontend/src/components/accounting/AcctTax.tsx#L133)
