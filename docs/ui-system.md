# รูปแบบหน้าจอและเกณฑ์ตรวจ UX

ปรับรอบ 23 พฤศจิกายน 2026 โดยใช้ UI/UX Pro Max และ Unslop สำหรับเว็บ POS ที่พนักงานใช้กับมือถือ แท็บเล็ต และ desktop ยังคง IBM Plex Sans Thai และสี terracotta เดิม ไม่ใช้คำแนะนำ landing-page หรือฟอนต์ตกแต่งจากผลค้นที่ไม่ตรงงาน POS

แนวทาง: เครื่องมือทำงานหน้าร้านที่อ่านเร็ว สุขุม และแม่นยำ พื้นผิวคล้ายกระดาษบิล ใช้สีที่สถานะโต๊ะและงานค้าง รายละเอียดราคาและเวลามีลำดับเดียวกันทุกโต๊ะ ลด gradient และเงาสีในโลโก้ ใช้ไอคอน SVG เดิม

แนวทาง Unslop อ้างอิงจาก [Damir Sokolovsky / Unslop](https://github.com/heydamir/unslop), CC BY 4.0 และ [UI/UX Pro Max](https://github.com/nextlevelbuilder/ui-ux-pro-max-skill), MIT

## ผังโต๊ะและงานค้าง

- ภาพรวมใช้ grid ที่ปรับจำนวนคอลัมน์ตามพื้นที่ การ์ดยืดตามข้อความจึงไม่ซ้อนทับกัน
- โหมดผังร้านจัดพิกัดเดิมลงช่อง grid หากช่องถูกใช้แล้วให้แยกลงแถวถัดไป โดยไม่เขียนพิกัดใหม่ลงฐานข้อมูล ผังเลื่อนภายในได้ ไม่ดันความกว้างทั้งหน้า
- แสดงสรุปทุกโต๊ะ แยกจากตัวกรองโซนและสถานะ เลือกโต๊ะเพื่อดูยอดก่อนเปิดส่วนย้ายออเดอร์หรือแก้ข้อมูล
- กระดิ่งและจำนวนใน sidebar ใช้ออเดอร์ที่ผู้ใช้มีสิทธิ์อ่านในร้านปัจจุบัน: ครัวนับออเดอร์ใหม่ เสิร์ฟนับออเดอร์พร้อมเสิร์ฟ รับชำระนับบิลที่เสิร์ฟแล้วหรือขอเช็คบิล โดยรวมตามโต๊ะและแยกกลับบ้าน
- การแจ้งเตือนนี้คือจำนวนงานค้าง ไม่ใช่จำนวนข้อความที่ยังไม่อ่าน กดแล้วไปหน้าทำงาน เมื่อไม่มีงานซ่อน badge และเมื่ออ่านล้มเหลวแสดงข้อผิดพลาดกับปุ่มลองใหม่ ไม่แสดงศูนย์แทนความผิดพลาด
- อัปเดตผ่าน Realtime สำรองด้วยการรีเฟรช 15 วินาทีเมื่อแท็บแสดงอยู่ และเมื่อกลับมาโฟกัส จำกัดเมนูและงานตามบทบาทเดิม ถ้าข้อมูลถูก server จำกัดจนไม่ครบ ให้แสดงข้อผิดพลาดแทนจำนวนที่ไม่จริง

## Alert และสถานะโหลด

- การยืนยันรายการเดิมใช้ SweetAlert2 แทน window.confirm มีปุ่มยกเลิกที่โฟกัสเริ่มต้น คืนโฟกัสเมื่อปิด และกันเปิดยืนยันซ้ำพร้อมกัน
- Alert ที่เปิดจาก native dialog อยู่ภายใน top layer เดียวกับ dialog เดิม แบบฟอร์มและรายละเอียดทั่วไปยังใช้ Modal.tsx
- ผังโต๊ะใช้ SweetAlert2 ยืนยันการย้าย / รวมออเดอร์และขอเช็คบิล พร้อมผลสำเร็จหรือข้อผิดพลาด
- Skeleton ใช้ระหว่างการอ่านข้อมูลครั้งแรกเท่านั้น ไม่แสดงรายการว่างก่อนคำขอเสร็จ เมื่ออ่านล้มเหลวต้องหยุด skeleton และแสดงข้อผิดพลาด การอัปเดตเบื้องหลังยังคงข้อมูลเดิมไว้
- คง schema gate, retry, reduced-motion และ accessible busy status โดยไม่แก้สัญญาความพร้อมของฐานข้อมูล

หลักฐานเพิ่มเติม: e2e/workspace-design.spec.ts ตรวจ geometry ที่ 375/768/1024/1440px, skeleton/error/retry, งานตามบทบาท และการยกเลิก/ป้องกันส่งซ้ำใน SweetAlert2 ใช้ข้อมูลจำลอง ไม่มีการเขียนฐานจริง

## กติกาที่ใช้ร่วมกัน

| ส่วน | การใช้งาน |
|---|---|
| Typography | ฟอนต์ไทยเดิม, ฐาน 16px, ข้อความย่อย 15px, คำอธิบายเล็ก 13px, line-height 1.5-1.6; ช่องกรอก 16px ลดการซูมอัตโนมัติบนมือถือ |
| Spacing | ใช้ระยะ 4/8/16/24/32px ตามลำดับความสำคัญ; gutter 16px บนมือถือและ 24px บนจอใหญ่ |
| Border radius | ช่องกรอก/ปุ่ม 10px, card/dialog 14px; ลด chip ที่โค้งมากเกินจำเป็น |
| Color/contrast | ปุ่มหลัก terracotta เข้ม, สำเร็จเขียวเข้ม, ลบแดงเข้ม; ตรวจปุ่มหลักกับตัวอักษรขาว ≥4.5:1 ทั้ง light/dark แยกกัน; ข้อความรองต้องไม่จางจนอ่านไม่ออก |
| Buttons | `.btn`/`.btn-sm` สูงและกว้างขั้นต่ำ 44px, loading/disabled ชัดเจน, ไม่ขยาย/ย่อปุ่มจนตำแหน่งเปลี่ยนตอนกด, รองรับข้อความหลายบรรทัด |
| Responsive | ทดสอบ 375/768/1024/1440px และ modal ในจอแนวนอน; ตารางเลื่อนภายใน ไม่ดันทั้งหน้า |
| Navigation | มี skip link, `aria-current`, กลุ่มเมนูอ่านชัด; เมนูมือถือใช้ dialog กักโฟกัสและคืนโฟกัสเมื่อปิด |
| Feedback | โหลด/บันทึก/ข้อผิดพลาดแสดงข้อความ; schema ไม่พร้อมบล็อกหน้าทำรายการพร้อมปุ่มลองใหม่ ไม่แสดงหน้าร้านที่โหลดข้อมูลได้ครึ่งเดียว |
| Inline validation | login, เปลี่ยนรหัสผ่าน และเงินเข้า/ออกกะแสดง error ผูกช่องด้วย `aria-describedby`/`aria-invalid`; submit พาไปจุดผิด; login มีสรุป error ที่โฟกัสได้ |

## Modal

ทุก dialog ใช้ `components/Modal.tsx`: React portal ไป `document.body`, native `showModal()` อยู่ top layer, กลาง viewport, สูงไม่เกิน viewport และเลื่อนภายในได้ ไม่ใช้ `z-index` แก้ปัญหา ancestor ที่มี transform/contain

ใช้ label ที่บอกหน้าที่, ปุ่มปิดมีชื่อ, Escape ปิดได้เมื่อไม่ได้บันทึก, ปิด dialog ซ้อนไม่ปิดตัวแม่, lock scroll แบบนับจำนวน dialog, คืนโฟกัสให้ปุ่มเปิด และหยุด submit/click/cancel ไม่ให้ไหลเข้าฟอร์มต้นทาง การพิมพ์ใบเสร็จยังใช้ print stylesheet

ห้ามเพิ่ม overlay แบบ `div.fixed` สำหรับฟอร์มใหม่ ให้ใช้ shared dialog และเพิ่ม regression หากมีพฤติกรรมต่างจากปกติ

## Schema compatibility

`DatabaseReady` ตรวจ `/api/readyz` ก่อน mount หน้าข้อมูล API ตรวจ metadata ของ columns/RPC พร้อม zero-row probe; `schema_version:0011` เป็น compatibility contract ไม่ใช่ใบรับรอง RLS หรือหลักฐาน migration history

ช่วงรอใช้ skeleton ของ navigation/header/cards ที่ปรับตามขนาดจอ มี `aria-busy` และข้อความ status สำหรับ screen reader; ปิด animation ตาม reduced-motion เมื่อพบปัญหาจริงจะเปลี่ยนเป็นสาเหตุและปุ่มลองใหม่ ไม่ปล่อยให้ skeleton ค้างไม่จบ

หน้า login เปิดได้โดยไม่โหลดข้อมูลร้าน ส่วน offline POS เปิดได้เฉพาะแท็บที่เคยยืนยัน schema ล่าสุดแล้ว มีเมนู snapshot และคิวเดิมตามคู่มือฟีเจอร์ ไม่ถือว่าคิวออฟไลน์ส่งถึงครัวแล้ว

## รายการข้อมูลและ pagination

- ประวัติบิลแสดงแถวสรุปและเปิดรายละเอียดเฉพาะบิล ไม่แสดงทุกรายการอาหารทุกบิลพร้อมกัน
- ค่าเริ่มต้น 10 รายการต่อหน้า เลือก 20 หรือ 50 ได้ มีปุ่มก่อนหน้าและถัดไปที่หัวรายการ จึงไม่ต้องเลื่อนลงไปท้ายรายการเพื่อเปลี่ยนหน้า
- Bills และ Audit ใช้ cursor ที่เรียงคงที่ หน้าใหม่แทนข้อมูลหน้าเดิม ไม่ต่อท้ายให้หน้าสูงขึ้นเรื่อยๆ
- Members และใบรับของใช้ server pagination; เปลี่ยนคำค้นหาหรือตัวกรองต้องกลับหน้าแรก
- ประวัติแต้ม สต็อก ใบนับ รายจ่าย ผู้ขาย พนักงาน เมนู และวัตถุดิบแบ่งหน้าชุดข้อมูลที่โหลดแล้ว ยอดรวมคำนวณจากชุดข้อมูลเดิม ไม่ใช่เฉพาะแถวที่มองเห็น
- หน้ารายจ่ายและประวัติสต็อกยังใช้กรอบวันที่และเพดานเดิม การแบ่งหน้าใน browser ไม่ได้ขยายช่วงข้อมูลของ API
- ตาราง/รายการมีความสูงจำกัดและ header คงที่เมื่อเลื่อน ใช้รายละเอียดแบบพับเมื่อข้อความยาว คงข้อความและตัวควบคุมที่จำเป็นไว้ ไม่บีบตัวอักษรให้เล็กเพื่อยัดข้อมูล
- รายการงานสดหน้าครัวและหน้ารับออเดอร์คงการแสดงงานตาม workflow ไม่ซ่อนงานเร่งด่วนด้วย pagination ของหน้าประวัติ

## หลักฐานการทดสอบ

- `e2e/modal-regression.spec.ts`: geometry กลาง viewport แม้อยู่ใน form ที่มี transform/paint containment, keyboard, focus, nested dialog, busy guard และ inline validation
- `e2e/ux-readiness.spec.ts`: schema mismatch ไม่อ่านข้อมูลร้าน, retry, responsive login, light/dark contrast, mobile navigation และ session ใหม่หลังเปลี่ยนรหัสผ่าน
- `e2e/audit-regression.spec.ts`: เส้นทาง POS/รับชำระ/CRM/ครัวที่ใช้งานจริงผ่าน API จำลอง

ผลเหล่านี้เป็นขอบเขตที่ทดสอบ ไม่ใช่การรับรอง WCAG ทุกข้อหรือยืนยันว่าไม่เกิดบั๊กได้อีกทุกกรณี
